# v1.0.7 검증 및 남는 경계

## 변경

- `portfolio.write_portfolio`: 일반 금융 저장 시 lock 안에서 최신 planning metadata를 읽어 유지. 같은 프로세스 내 planning 저장과 오래된 계좌 저장의 교차 실행을 방어한다.
- `replace_planning=True`: 백업 복원과 명시적 초기화에만 사용. 구버전 백업에 planning이 없으면 복원 후 planning도 없다.
- `planning.mutate`: 기존 날짜/owner의 기록 정정·삭제. revision과 확인을 검증하며 미존재 기록 정정, NaN/불일치 금액은 거절. 정정은 당시 환율·평가시각·저장시각을 유지하고 edited_at/source만 보충한다.
- 버킷 초안은 시작한 가족 범위와 revision을 유지한다. 화면 이동 시 상단 미저장 안내, 종료 시 브라우저 경고. 다시 불러오기 성공 시에만 초안을 폐기한다.
- 기록 정정/삭제는 실제 계좌나 ledger에 영향을 주지 않는다. 삭제 복구에는 별도 백업이 필요하다.

## 수행한 검증

- Python unittest 전체 82개 통과. 기존 77개 + 신규 5개.
- Node 계산 테스트 5개 통과. 합계 87개, 실패/expected failure 없음.
- JavaScript 문법 및 `git diff --check` 통과.
- 신규 테스트: 오래된 금융 저장 뒤 planning 유지, 명시적 복원 시 제거, 기록 정정의 식별자/환율/계좌 보존, 삭제 확인/대상/revision 검증, 잘못된 정정의 파일 무변경.
- 백업 API mock 기대값에 명시적 복원 옵션을 반영했다.
- `tests/planning_ui_preview.py`: 실제 app.main/.env/사용자 data를 읽지 않고 임시 portfolio만 생성하는 브라우저 검증 서버. planning 서비스만 연결하고 다른 쓰기는 403, 외부 요청은 기존 fixture CSP로 제한한다.
- 실제 브라우저에서 가상 버킷 저장 → 새로고침 유지, 순자산 생성 → 정정 → 새로고침 → 삭제 → 새로고침, 가족 변경 중 초안 범위 유지 및 다시 불러오기 복귀를 확인했다. 브라우저 확인은 도구로 수행했으며 CI 자동 E2E 테스트는 아니다.
- 실제 금융 API 및 Linux 서버 Docker build/deploy는 실행하지 않았다.

## 실제 파일 비교

작업 전후 경로/크기/SHA-256을 비교했다. 보호 대상 40개 중 historical_fx_cache.json과 asset_records.json 두 파일의 변경이 관찰됐다. 원인은 확정하지 않았으며 실제 내용을 출력하거나 파일을 되돌리지 않았다. .env와 portfolio/ledger 등 나머지는 동일했다. 추가 전체 테스트 직전·직후 비교에서는 40개 모두 동일했다. 전체 작업 동안 모든 data가 불변이었다고 주장하지 않는다.

## 한계 / 다음 검토

- 모든 기존 금융 writer 사이의 lost update, 여러 프로세스/컨테이너, portfolio-ledger 간 crash atomicity까지 해결한 것은 아니다. 같은 data를 쓰는 서버는 단일 worker로 유지한다.
- 백업 복원/초기화는 명시적 파괴적 교체이므로 다른 편집·동기화를 중지한 상태에서 수행한다. 전체 데이터 공통 revision은 아직 없다.
- 각 자산의 실제 갱신 시각이 일관되게 저장되어 있지 않다. 기록의 기존 valuation_at/recorded_at/edited_at만 표시하며 이를 자산별 최신 시각으로 해석하지 않는다. 이 부분은 별도 저장 정책 설계 후 추가해야 한다.
- 잘못된 과거 기록의 원본을 자동 추정하거나 복구하지 않는다. 정정 이력 전체 감사 로그와 삭제 undo는 없다.
- 버킷 저장 진행 중 추가 편집을 하는 복잡한 동시 UI 조작까지 자동 E2E로 검증한 것은 아니다.
