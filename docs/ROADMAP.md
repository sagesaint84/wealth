## 1. 현재 우선순위

### Phase 10.5A-4.1 — 공식 공시 기반 배당예상 Source 계층

상태: 진행 중 / PR #22

목표:

- 국내 배당 예상에 OpenDART 공식 자료를 보강한다.
- 기존 Naver/Yahoo 예상은 fallback으로 유지한다.
- 공식 과거 DPS와 미래 확정 배당을 구분한다.
- 최근 배당결정 공시 존재 여부를 표시한다.
- 사용자별 기존 DART credential을 재사용한다.
- 공식 source 장애가 배당 예상 전체 장애로 번지지 않게 한다.

완료 기준:

- 신규 source tests 통과
- 기존 DART user OpenAPI tests 통과
- 금융소득 projection 회귀 통과
- 전체 unittest suite 통과
- 사용자 로컬 검증 완료
- PR Ready → merge
- GHCR build success
- 운영 배포 후 예상탭 source 표시 확인

## 2. 다음 단계

### Phase 10.5A-4.2 — 고배당 분리과세 What-if 연결

목표:

- A-4 고배당 분리과세 규칙 엔진을 A-3 What-if 화면/API에 연결한다.
- 적격 여부를 앱이 배당수익률 등으로 임의 추정하지 않는다.
- 공식자료 확인 상태와 사용자의 적용 가정을 분리한다.
- 일반 금융소득 screening과 특례배당 분리과세 결과를 동시에 보여준다.

권장 UI:

- 고배당기업 공식 확인 상태
- 특례 적용 가정 ON/OFF
- 일반 금융소득 2,000만원 screening 대상 금액
- 특례로 제외되는 배당금액
- 특례 국세 예상액
- 지방소득세/최종 신고세액 미포함 경고

완료 기준:

- 신청하지 않은 경우 기존 계산과 동일
- 공식 확인 없이 특례를 자동 적용하지 않음
- 경계값 테스트
- 기존 금융소득 What-if 회귀 통과

### Phase 10.5A-4.3 — 미래 배당 확정공시 구조화

목표:

- 단순 `배당결정 공시 존재`를 넘어 공시 본문에서 주당 배당금, 기준일, 지급 예정일 등 구조적으로 검증 가능한 값을 수집한다.
- 구조 검증 성공한 경우에만 `confirmed_amount=true`로 처리한다.
- 확정 공시값은 과거 TTM/휴리스틱보다 우선한다.

원칙:

- 제목 매칭만으로 금액 확정 금지
- 정정공시가 있으면 최신 유효 공시 우선
- 지급일이 명확하지 않으면 임의 날짜 생성 금지
- 실패 시 기존 Naver/과거 패턴 fallback

### Phase 10.5A-4.4 — 국내 ETF 분배금 공식 Source 개선

목표:

- 국내상장 ETF/리츠 등 DART corp-code만으로 충분하지 않은 상품의 공식 분배금 source를 검토한다.
- 거래소/운용사 공시가 구조적으로 안정적인 경우 Source 계층에 추가한다.
- 공식 source가 불안정하면 현재 Naver TTM fallback을 유지한다.

## 3. 금융소득/가족 세금 확장

### Phase 10.5B-1 — 가족 금융소득 위험 보기

- 본인/배우자/자녀 등 소유자별 예상 금융소득
- 1,000만원 watch / 2,000만원 screening 상태
- 가족 전체 합계는 참고값으로만 제공하고 개인별 세법 기준과 혼동하지 않음

### Phase 10.5B-2 — 추가 배당/매매 What-if 확장

- 추가 배당금
- 추가 이자
- 추가 해외주식 실현차익
- 국내상장 해외 ETF 과세기준금액
- 개인 vs 가족법인 비교와 연결

### Phase 10.5B-3 — 배우자/자녀 분산 시뮬레이션

- 자산 또는 미래 투자금 배분 시 개인별 금융소득 변화
- 단순 세금 절감 추천이 아니라 결과 비교 중심
- 증여세/명의신탁/실질귀속 등 법적 쟁점은 계산 범위에서 별도 표시
- 실제 증여세 계산은 별도 규칙 엔진 없이는 자동 확정하지 않음

### Phase 10.5B-4 — 개인 종합과세 정밀화

후보 범위:

- 금융소득 종합과세 누진구간
- 기본세율 비교
- 원천징수 기납부세액
- 지방소득세
- 외국납부세액공제

원칙:

- 세법 연도별 rule module 분리
- UI에 세율 상수 하드코딩 금지
- 공식 자료 검증일 기록
- 법률/세무 최종 판단과 screening을 구분

## 4. 후속 세무·사회보험 영역

### 건강보험 영향

- 직장가입자/지역가입자 구분이 필요하므로 별도 모델링
- 단순 금융소득 2,000만원 기준과 동일시하지 않음
- 연도별 보험료 기준 검증 필요

### 인적공제/부양가족 영향

- 소득요건과 금융소득 과세 방식의 관계를 별도 rule로 모델링
- 배우자/자녀 분산 기능과 연결 가능

### 법인 자금 인출 확장

현재 가족법인 비교는 법인 유보 및 배당 인출 중심이다.
후보:

- 급여
- 상여
- 퇴직금
- 대여금/가지급금 위험

법률·세무 복잡도가 높으므로 단계별로 분리한다.

## 7. 장기 구조 개선 후보

### stable user id 기반 저장 경로

현재 user data path는 `data/users/<username>/...`이다.
향후 stable UUID id 기반으로 바꾸려면 다음을 반드시 별도 migration으로 처리한다.

- 기존 디렉터리 rename/move
- rollback 전략
- 중복/누락 검증
- 각 서비스의 username/path 의존성 제거
- 백업 후 migration

현재 단계에서는 경로를 임의 변경하지 않는다.

### 세법 rule source metadata

모든 세법 모듈에 다음 정보를 일관되게 보관하는 방향을 유지한다.

- rule year
- verified date
- official source URL
- 계산 범위
- not calculated 목록
- screening/legal determination 구분

## 8. 우선순위 변경 규칙

우선순위를 바꿀 때는:

1. `PROJECT_STATE.md` 현재 단계 수정
2. 이 문서 순서 수정
3. 관련 PR/Issue에 이유 기록
4. 이미 구현된 API 계약을 깨뜨리는 경우 migration/compatibility plan 기록

실제 secret, 계좌번호, 토큰, 개인 금융 데이터는 roadmap에 기록하지 않는다.
