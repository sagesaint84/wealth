# 순자산 기록 / 전략 버킷 구현과 검증

## 배치

상단에 `시세 갱신`과 `계좌 동기화`를 구분해서 배치했다. 기존 조회는 실제로 `/api/refresh-prices`를 호출하므로 단순 조회라고 표시하지 않는다. 동기화는 `/api/sync/all`로 기존 동작을 유지하고, 갱신된 dashboard 로드 후 성공 상태를 표시한다. 실패·부분 실패·미설정은 성공과 구분한다. 마지막 성공 시각 표시는 현재 화면 세션 기준이다.

홈 요약 → 순자산 추이 → 자산 구성 순으로 배치했다. 투자에는 포트폴리오 / 전략 버킷 / 주식기록 선택을 추가했다.

## 기록 정책

- 기존 asset_records는 주식기록이므로 전체 순자산 추이에 재활용하지 않는다.
- 자동 수집이 아닌 **사용자가 확인한 현재 화면 값을 날짜별로 저장**한다. 자동화가 불완전한 상황에서 전체 자산의 확정 일별 결산이라고 오인하지 않도록 선택한 범위이다.
- 한국 시간 날짜 + owner별 한 기록. 기존 당일 기록은 확인 후 교체한다. 기록되지 않은 과거는 비워둔다.
- 당시 자산·부채·순자산·환율·평가 기준 시각·저장 시각·계산 버전을 보존한다.
- 미래의 환율이나 현재 잔고로 과거 기록을 다시 계산하지 않는다. 그래프 연결선은 저장된 관측점의 시각화이지 미기록 일자의 데이터가 아니다.
- 서버는 유한한 값, 양수 환율, 자산-부채=순자산을 검증한다. 총액은 기존 frontend 계산을 그대로 사용하며 새 금융 계산 정책을 만들지 않았다.
- 현재 세션에서 동기화 진행/실패/부분 실패/미설정이면 오늘 기록 버튼을 차단한다. 서버가 금융기관 결산의 완전성을 검증하는 기능은 아니다.

## 전략 버킷 정책

- 초기 분류는 모두 미분류. 사용자가 버킷 이름/목적/목표를 추가하고 명시적으로 저장한다.
- 증권 보유종목 및 KRW/USD 예수금만 대상. 비중 분모는 선택한 가족의 대상 전체(미분류 포함).
- 계좌 기본값보다 보유내역 ID 예외가 우선한다. 종목코드로 분류하지 않아 복수 계좌 동일 종목이 서로 다른 목적을 가질 수 있다.
- 예수금은 계좌 버킷에 포함한다. 보유종목은 계좌 합계와 중복 합산하지 않는다.
- 목표 합계는 최대 100%, 버킷 최대 30개. 예외의 `미분류`와 `계좌 기본값 사용`을 구분한다.
- 목표는 사용자 공통이며 현재 비중만 가족 조회에 따른다. 부동산 공동명의나 owner="모두" 정책은 재설계하지 않는다.
- 보유내역 ID가 사라지면 기존 예외를 다른 내역으로 옮기지 않는다. 잔고나 ledger는 수정하지 않는다.

## 저장 및 호환성

`portfolio.json.settings.wealth_planning` optional metadata를 사용한다. 기존 portfolio/asset/ledger 레코드의 필드나 잔고는 수정하지 않고, migration도 없다. planning 저장은 portfolio의 기존 저장 lock 안에서 최신 파일을 읽고 temp 파일로 교체한다. 저장한 revision이 달라지면 HTTP 409로 재확인을 요구한다. planning 변경은 시세 갱신이 아니므로 portfolio의 updated_at을 변경하지 않는다.

기존 백업 경로가 portfolio settings를 포함하므로 별도 형식 변경 없이 보존된다. 구버전 백업을 복원하면 그 백업에 없는 planning 기록은 복원되지 않는다. 실제 사용자 백업으로 시험하지 않았다.

## 검증

- Python suite: 77개 통과 (신규 planning 9개 포함).
- Node 순수 계산 테스트: 5개 통과. 계좌 기본/보유내역 예외/동일 종목 복수 계좌, owner 범위, 미분류, FX 누락, 입력 무변경 확인.
- 서비스 테스트는 TemporaryDirectory 사용. 사용자 A/B 격리, 비정상 입력 실패 시 파일 불변, 일별 교체 확인, revision 충돌, 백업 데이터 roundtrip, 파일 교체 실패 rollback 경계 확인.
- 가상 브라우저에서 홈 그래프, 전략 탭, 버킷 입력/선택지 갱신, 모바일 가로 overflow 부재, 저장 실패 안내 및 입력 유지 확인.
- preview 서버는 실제 앱/API credential을 읽지 않고 저장 요청을 거절한다. 브라우저의 성공 저장 경로를 실제 데이터로 실행하지 않았다.
- 외부 증권사 동기화 자체와 실제 금융 API 호출은 실행하지 않았다. 기존 PWA preview의 Service Worker 404는 그대로이다.

## 남는 한계

작업 전후 경로/크기/SHA-256 비교에서 `.env`, portfolio, ledger 등은 동일했고 `historical_fx_cache.json` 하나의 변경이 관찰됐다. 원인은 확정하지 않았으며 캐시를 되돌리지 않았다. 별도로 마지막 전체 테스트의 직전·직후에는 보호 대상 40개 파일 모두 동일했다. 민감한 실제 내용은 출력하지 않았다.

- 자동 일별 결산, 과거 기록 수정/삭제 관리, 가족별 별도 목표 프로필, 자동 리밸런싱/매매는 이번 구현에 포함되지 않는다.
- 일부 기존 portfolio 변경 서비스는 lock 밖에서 읽고 나중에 쓰는 방식이다. planning끼리의 revision 충돌은 방어하지만 기존 모든 쓰기 경로의 동시 변경까지 완전한 트랜잭션으로 바꾸지는 않았다.
- 기존 순자산 계산/owner 정책의 의미상 한계는 기록에도 그대로 반영된다. UI 값과 별개의 새 계산식을 만들지 않았다.
